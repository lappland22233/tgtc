# Telegram Bot API 流式文件端点调用指南

## 1. 功能说明

本项目新增了独立的流式文件下载端点，可在 TDLib 尚未完成整文件下载时，将已经连续下载完成的字节按顺序发送给调用方，从而降低冷文件的首字节等待时间。

该功能具有以下特性：

- 默认关闭，必须通过启动参数显式启用。
- 不修改标准 Bot API `getFile` 方法的行为。
- 接口正常结束时保证响应体字节数等于文件精确大小。
- 文件始终从偏移量 `0` 开始顺序输出，不重复、不跳字节。
- 同一文件的多个调用方共享 TDLib 下载任务，但各自维护独立的输出进度。
- 当前版本仅支持完整文件 `GET`，**不支持 `Range`、断点续传、`HEAD` 或多区间请求**；断点续传（`206` / `Content-Range` / `ETag` / `If-Range`）由**外层后端缓存层**提供（见第 10 节）。
- 输出平台为 **64 位（x86_64）**，端点内部按 `int64` 处理文件大小：单文件可服务到 4GiB 以上，实际边界受 workdir 可用空间、`--file-stream-max-size` 与 Telegram 本身能力约束；但**单个 HTTP 响应仍是顺序完整流**，无法从中间随机读取。

## 2. 启动服务

### 2.1 最简启动命令

```powershell
.\telegram-bot-api.exe `
  --api-id=<API_ID> `
  --api-hash=<API_HASH> `
  --enable-file-streaming
```

默认监听端口为 `8081`。如需修改：

```powershell
.\telegram-bot-api.exe `
  --api-id=<API_ID> `
  --api-hash=<API_HASH> `
  --http-port=8081 `
  --enable-file-streaming
```

`API_ID` 和 `API_HASH` 是 Telegram 应用凭据，不是 Bot Token，可从 `https://my.telegram.org` 获取。

### 2.2 完整配置示例

```powershell
.\telegram-bot-api.exe `
  --api-id=<API_ID> `
  --api-hash=<API_HASH> `
  --http-port=8081 `
  --enable-file-streaming `
  --file-stream-allow-ip=127.0.0.1 `
  --file-stream-chunk-size=262144 `
  --file-stream-max-connections=100 `
  --file-stream-first-byte-timeout=30 `
  --file-stream-idle-timeout=60 `
  --file-stream-write-high-watermark=1048576
```

发布包内 `scripts/release/start.sh` 生成的 systemd 单元会显式覆盖下列值（可与上面的最小示例对照）：

```text
--local --http-port=8081 --dir=<runtime>/telegram-bot-api/data
--enable-file-streaming --temp-dir=<runtime>/telegram-bot-api/tmp
--file-stream-first-byte-timeout=120 --file-stream-idle-timeout=120
--file-stream-max-connections=100 --file-stream-max-size=0
--workdir-cleanup-threshold-bytes=21474836480 --workdir-cleanup-target-bytes=16106127360
--workdir-cleanup-interval=3600 --workdir-file-ttl=86400
--workdir-min-free-bytes=1073741824 --workdir-unknown-file-min-free-bytes=536870912
```

`--http-stat-port` **仅在部署时设置 `TGTC_BOT_STATS_PORT` 才追加**（默认关闭）。

### 2.3 配置参数

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `--enable-file-streaming` | 关闭 | 启用流式文件端点。 |
| `--file-stream-allow-ip` | 回环与私网来源 | 允许访问流式端点的单个 IP 或逗号分隔 CIDR 白名单；生产环境应仅填写受控业务后端或反向代理的固定地址范围。 |
| `--file-stream-chunk-size` | `262144` | 单次读取和发送的最大字节数，允许范围为 **16384 字节（16 KiB）～1048576 字节（1 MiB）**。 |
| `--file-stream-max-connections` | `100` | 全局同时活动的流式响应数量上限。 |
| `--file-stream-first-byte-timeout` | `30` | 首个数据块发送前的最长等待时间，单位为秒。 |
| `--file-stream-idle-timeout` | `60` | 已开始传输后，两个数据块之间允许的最长停滞时间，单位为秒。 |
| `--file-stream-write-high-watermark` | `1048576` | 每个连接单次进入受控写入队列的数据上限（须不小于 `--file-stream-chunk-size`）。 |
| `--file-stream-max-size` | `0` | 流式端点允许服务的单文件最大字节数，**始终生效（含 `--local` 模式）**；`0` 表示不限制。 |
| `--temp-dir` | 系统临时目录 | HTTP 服务器临时文件目录。发布包固定落在受控路径 `<runtime>/telegram-bot-api/tmp`（默认 `/tmp` 会脱离 workdir 配额与清理统计）。 |
| `--workdir-cleanup-threshold-bytes` | `21474836480`（20 GiB） | workdir 占用达到该阈值时触发异步清理。 |
| `--workdir-cleanup-target-bytes` | `16106127360`（15 GiB） | 阈值清理后 workdir 的目标占用量。 |
| `--workdir-cleanup-interval` | `3600`（秒） | 周期性 workdir 清理间隔。 |
| `--workdir-file-ttl` | `86400`（秒） | 非活动 workdir 文件的保留时间。 |
| `--workdir-min-free-bytes` | `1073741824`（1 GiB） | workdir 最低空闲余量；不足时不再开始新的本地副本（写前准入）。 |
| `--workdir-unknown-file-min-free-bytes` | `536870912`（512 MiB） | **未知大小**文件在 `--workdir-min-free-bytes` 之外额外要求的空闲余量（写前准入）。 |
| `--http-stat-port` | 未启用 | HTTP 统计端点端口；启用后**必须自行限制仅本机可访问**（详见第 2.5 节）。 |
| `--dir` | 必填（生产） | TDLib workdir。与后端 `TELEGRAM_LOCAL_FILE_DIR` 必须完全一致，且不得清空/重命名（否则历史 `file_id` 全部失效）。 |

### 2.4 workdir 空间准入与清理

- **写前空间准入（fail-closed）**：开始为文件建立本地副本**之前**检查 `可用空间 − --workdir-min-free-bytes ≥ 预计增量`；文件大小未知时，以 `--workdir-unknown-file-min-free-bytes`（默认 512 MiB）作为预计增量。
- 不满足时在**首字节写出之前**返回结构化 **`507`**（JSON + 真实 HTTP 状态码），并递增 `workdir_space_rejections` 且告警。因此多个并发大文件 `getFile` 不会「都在开始时看似可行」，最终把 workdir 写到爆满。
- 已被接受的下载中途不再重复检查（其准入在开始时已完成）。
- **周期性清理**删除非活动的本地媒体副本（`--workdir-cleanup-*` / `--workdir-file-ttl` 控制）。**控制状态不在清理范围**：`db.sqlite*` 与 `td.binlog*`（以及 session）是 `file_id` 的绑定凭据，删除/清空/重命名会让历史 `file_id` 全部失效；可回收的只是媒体副本。

### 2.5 workdir 副本回收（删除握手）与统计字段

- 携带 `X-Telegram-No-Cache` 的流式请求**正常完成**后，若该文件**没有其他流监听者或 `getFile` 下载监听者**，服务端会删除 TDLib workdir 中的本地副本（引用计数安全）；中断传输的行为与不带该头一致。
- **删除握手**：响应对象中的 `local_cache_released` 字段表示本地副本是否已释放；后端侧由 `remove_file_stream_listener` 与 `releaselocalfile`（`releaseLocalFile`）覆盖 `getFile` 的普通下载。删除的尝试 / 成功 / 失败均有计数，**待释放（pending）计入失败**，保证它在下一次重试成功前持续可见。
- **`--http-stat-port` 的 stats 输出新增字段**（由第 2.3 节的端口提供，需自行限制仅本机访问）：

  | 字段 | 含义 |
  |---|---|
  | `workdir_free_bytes` | workdir 所在卷当前空闲字节 |
  | `workdir_min_free_bytes` | 写前准入要求的 `--workdir-min-free-bytes` |
  | `workdir_space_rejections` | 因空间不足被拒绝的下载次数 |
  | `active_file_streams` | 当前活动的流式文件数 |
  | `active_file_stream_listeners` | 所有 Bot 上（文件 → 流）监听注册总数 |
  | `file_stream_first_byte_timeouts` | 首字节超时次数 |
  | `file_stream_idle_timeouts` | 传输停滞（空闲）超时次数 |
  | `file_delete_attempts` | 本地副本删除尝试次数 |
  | `file_delete_successes` | 本地副本删除成功次数 |
  | `file_delete_failures` | 本地副本删除失败次数（含 pending） |

## 3. 获取 `file_id`

流式端点接收 Telegram Bot API 返回的 `file_id`，不是标准 `getFile` 返回的 `file_path`，也不是本地文件路径。

常见来源包括：

- `getUpdates` 返回消息中的 `document.file_id`；
- `message.video.file_id`；
- `message.audio.file_id`；
- `message.photo[n].file_id`；
- 其他 Bot API 对象中的 `file_id` 字段。

示例对象：

```json
{
  "document": {
    "file_name": "example.zip",
    "file_id": "BQACAgIAAxkBAA...",
    "file_unique_id": "AgAD...",
    "file_size": 10485760
  }
}
```

调用时应使用 `file_id`，不能使用 `file_unique_id`。

## 4. 请求格式

### 4.1 正式数据中心

```text
GET /stream/file/bot<BOT_TOKEN>/<URL_ENCODED_FILE_ID>
```

完整 URL：

```text
http://<HOST>:<PORT>/stream/file/bot<BOT_TOKEN>/<URL_ENCODED_FILE_ID>
```

### 4.2 Telegram 测试数据中心

```text
GET /stream/file/bot<BOT_TOKEN>/test/<URL_ENCODED_FILE_ID>
```

只有 Bot 和文件来自 Telegram 测试数据中心时才使用 `/test/` 路径。

### 4.3 参数要求

| 参数 | 说明 |
| --- | --- |
| `BOT_TOKEN` | BotFather 发放的完整 Bot Token，例如 `123456789:AA...`。 |
| `URL_ENCODED_FILE_ID` | 对完整 `file_id` 做 URL 路径段编码后的结果。 |
| `X-Telegram-File-Size` | 可选请求头，十进制正整数，单位为字节。全新 TDLib 工作目录下载历史文件时，应由可信业务后端从上传记录中提供。 |
| `X-Telegram-No-Cache` | 可选请求头，值为 `1` 或 `true` 时开启（其他值视为未开启）。开启后，该请求**正常完成整文件传输**且该文件没有其他流监听者或下载监听者时，服务端会删除 TDLib 工作目录中的本地缓存副本，避免完整传输的文件永久占用磁盘。 |

必须对 `file_id` 进行 URL 编码，尤其不要直接拼接包含 `/`、`+`、`=`、`%` 等特殊字符的值。

大小选择规则：当 TDLib 与 `X-Telegram-File-Size` 都提供正整数时，两者必须一致，随后使用 TDLib 值；不一致时在响应开始前返回 `502`。仅 TDLib 已知时使用 TDLib 值；仅请求头已知时使用可信业务后端提供的请求头值，使冷文件能够立即启动下载与流式传输；两者都未知时返回 `502 Exact file size is unavailable from Telegram`。不要让浏览器或公网调用方自由声明大小，端点应仅供业务后端通过受限内网访问。

`X-Telegram-No-Cache` 语义补充说明：

- 仅影响**正常完成传输之后**的本地副本清理；传输中断时的行为与不带该头完全一致（仍为取消下载并由 TDLib 删除未完成分片）。
- 只删除 TDLib 本地缓存文件，**不影响 Telegram 云端文件**，后续仍可再次通过 `file_id` 重新下载。
- 若该文件同时存在其他流监听者或标准 `getFile` 下载监听者，不会删除，沿用现有监听者判断逻辑。
- 不带该头的请求行为完全不变（完整传输成功的文件继续保留在工作目录中）。

### 4.4 Telegram 风控兼容机制

每个文件只启动一次 TDLib 标准整文件下载：`downloadFile(file_id, 1, 0, 0, false)`。HTTP 流根据 `updateFile` 的连续可读前缀，从 TDLib 本地缓存文件使用本地 `pread` 分块输出；**不会调用 `readFilePart`，也不会把每个 HTTP 分块转换成额外的 MTProto `upload.getFile` 请求**。同一文件的并发 HTTP 消费者共享这一次下载，从而保持流式首字节和背压能力，同时避免非官方式高频 DC 分片访问触发服务端风控或重置连接。

运维验收应确认：源码及运行日志中没有流式路径的 `readFilePart` 调用；单个大文件在 Telegram 侧只表现为一次正常整文件下载。

## 5. 调用示例

### 5.1 PowerShell 下载到文件

```powershell
$baseUrl = "http://127.0.0.1:8081"
$botToken = "<BOT_TOKEN>"
$fileId = "<FILE_ID>"
$encodedFileId = [System.Uri]::EscapeDataString($fileId)
$url = "$baseUrl/stream/file/bot$botToken/$encodedFileId"

curl.exe --fail --location --output ".\download.bin" $url
```

建议使用系统自带的 `curl.exe`，避免 Windows PowerShell 将 `curl` 解析为 `Invoke-WebRequest` 别名。

### 5.2 PowerShell 使用 `Invoke-WebRequest`

```powershell
$baseUrl = "http://127.0.0.1:8081"
$botToken = "<BOT_TOKEN>"
$fileId = "<FILE_ID>"
$encodedFileId = [System.Uri]::EscapeDataString($fileId)
$url = "$baseUrl/stream/file/bot$botToken/$encodedFileId"

Invoke-WebRequest -Uri $url -Method Get -OutFile ".\download.bin"
```

### 5.3 JavaScript / Node.js

```javascript
import { createWriteStream } from "node:fs";
import { pipeline } from "node:stream/promises";

const baseUrl = "http://127.0.0.1:8081";
const botToken = process.env.BOT_TOKEN;
const fileId = "<FILE_ID>";
const fileSize = 10485760;
const url = `${baseUrl}/stream/file/bot${botToken}/${encodeURIComponent(fileId)}`;

const response = await fetch(url, {
  headers: { "X-Telegram-File-Size": String(fileSize) }
});
if (!response.ok) {
  throw new Error(`下载失败：HTTP ${response.status} ${await response.text()}`);
}
if (!response.body) {
  throw new Error("响应体为空");
}

const expectedLength = Number(response.headers.get("content-length"));
let receivedLength = 0;
const counter = new TransformStream({
  transform(chunk, controller) {
    receivedLength += chunk.byteLength;
    controller.enqueue(chunk);
  }
});

await pipeline(
  response.body.pipeThrough(counter),
  createWriteStream("download.bin")
);

if (Number.isFinite(expectedLength) && receivedLength !== expectedLength) {
  throw new Error(`文件不完整：期望 ${expectedLength} 字节，实际 ${receivedLength} 字节`);
}
```

### 5.4 Python

```python
import os
from urllib.parse import quote

import requests

base_url = "http://127.0.0.1:8081"
bot_token = os.environ["BOT_TOKEN"]
file_id = "<FILE_ID>"
url = f"{base_url}/stream/file/bot{bot_token}/{quote(file_id, safe='')}"

with requests.get(url, stream=True, timeout=(10, 120)) as response:
    response.raise_for_status()
    expected_length = int(response.headers["Content-Length"])
    received_length = 0

    with open("download.bin", "wb") as output:
        for chunk in response.iter_content(chunk_size=256 * 1024):
            if not chunk:
                continue
            output.write(chunk)
            received_length += len(chunk)

    if received_length != expected_length:
        raise RuntimeError(
            f"文件不完整：期望 {expected_length} 字节，实际 {received_length} 字节"
        )
```

安装依赖：

```powershell
python -m pip install requests
```

## 6. 成功响应

成功请求返回：

```http
HTTP/1.1 200 OK
Content-Type: application/octet-stream
Content-Length: <文件精确字节数>
```

响应体是完整文件的原始二进制内容，不是 JSON，也没有 Bot API 的 `ok` 包装字段。

服务端只有在实际发送的字节数严格等于 `Content-Length` 时才会正常结束响应。

## 7. 完整性校验

### 7.1 必须检查 `Content-Length`

如果 Telegram 或 TDLib 在响应头发出后失败，HTTP 状态码无法再次修改。此时服务端会中断连接，调用方必须把以下情况视为下载失败：

- 实际收到的字节数小于 `Content-Length`；
- HTTP 客户端报告连接提前关闭；
- 输出流写入失败；
- 请求超时。

不要在发生上述情况时保留或使用不完整文件。推荐先写入临时文件，校验完成后再原子重命名：

```powershell
$tempFile = ".\download.bin.part"
$finalFile = ".\download.bin"

curl.exe --fail --output $tempFile $url
if ($LASTEXITCODE -ne 0) {
  Remove-Item $tempFile -ErrorAction SilentlyContinue
  throw "下载失败"
}
Move-Item $tempFile $finalFile -Force
```

### 7.2 可选哈希校验

如果业务侧保存了源文件哈希，可在下载完成后进行 SHA-256 校验：

```powershell
Get-FileHash ".\download.bin" -Algorithm SHA256
```

流式端点保证传输顺序和字节计数，但 Telegram Bot API 本身不会为该端点提供业务侧预期 SHA-256，因此端到端哈希需要由调用方自行保存和比对。

## 8. 错误响应

在流式响应开始前发生的错误使用 Bot API 风格 JSON：

```json
{
  "ok": false,
  "error_code": 400,
  "description": "Bad Request: ..."
}
```

常见状态码：

| 状态码 | 含义 | 建议处理 |
| ---: | --- | --- |
| `400` | 路径、URL 编码或 `file_id` 不合法。 | 修正参数，不要直接重试同一请求。 |
| `401` | Bot Token 无效或认证失败。 | 检查 Token 和调用环境。 |
| `404` | 路由未启用、文件不可用或无法解析。 | 检查启动参数、`file_id` 和数据中心。 |
| `405` | 使用了非 `GET` 方法。 | 改为 `GET`。 |
| `413` | 文件大小超出当前平台可处理范围。 | 更换平台或限制文件大小。 |
| `429` | 活动流数量超过配置上限。 | 指数退避后重试。 |
| `502` | TDLib 或 Telegram 上游下载失败，或 TDLib 与可信大小提示不一致，或两者均无法提供精确大小。 | 大小冲突先核对业务记录；其他情况短暂退避后重试，持续失败时检查文件是否仍可访问。 |
| `503` | Bot API Client 正在关闭。 | 服务恢复后重试。 |
| `504` | 首字节等待或传输停滞超时。 | 检查网络后重试，可按需调整超时参数。 |
| `507` | workdir 可用空间不足，**写前准入**被拒绝（fail-closed，发生在首字节之前）。 | 释放 workdir 空间或扩大卷后重试；不要盲目重试同一请求。 |

响应头发出后的错误不会返回第二个 JSON 错误体，而是直接终止连接。

## 9. 推荐重试策略

建议仅对 `429`、`502`、`503`、`504` 和网络连接错误进行有限重试：

1. 第一次失败后等待 1 秒；
2. 第二次失败后等待 2 秒；
3. 第三次失败后等待 4 秒；
4. 加入少量随机抖动；
5. 每次重试都重新从完整文件起点下载。

当前版本不支持断点续传，因此重试时不能携带 `Range` 请求头。

## 10. 反向代理注意事项

如果通过 Nginx、网关或 CDN 暴露端点，应关闭响应缓冲，否则代理可能先缓存大量数据再发送，抵消流式下载降低首字节时间的效果。

**内部流式端点**（仅供受控后端调用，不直接暴露公网）Nginx 示例：

```nginx
location /stream/file/bot {
    proxy_pass http://127.0.0.1:8081;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
}
```

**面向最终用户的公开入口是后端缓存层的 `/api/bot-dl/<token>`**（而非把 `/stream/file/...` 直接暴露出去）。该路径同样必须「直通」：不得改写或剥离 `Range` / `If-Range` / `ETag` / `Accept-Ranges` / `Content-Range`，不得开启响应缓冲、代理缓存或完整响应落临时文件，且 `proxy_read_timeout` 必须大于后端 Node 空闲超时（默认 180s）。参考片段：

```nginx
location ^~ /api/bot-dl/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_request_buffering off;
    proxy_cache off;
    proxy_max_temp_file_size 0;
    gzip off;                       # gzip 会移除 ETag
    proxy_read_timeout 210s;        # 不设置固定总时长
    proxy_connect_timeout 10s;
    access_log /var/log/nginx/bot-dl.access.log;
}
```

工程内已提供完整模板与部署自检脚本（仓库路径 `scripts/release/nginx-download.conf.template` 与 `scripts/release/check-download-proxy.sh`），模板额外包含日志脱敏 `map`、`/api/s/` 片段与代理临时目录容量告警清单。

生产环境必须使用 HTTPS，并避免在访问日志、监控、错误页面或前端代码中泄露 Bot Token。由于 Token 位于 URL 路径中，应对代理访问日志进行脱敏或关闭该路径的详细日志。

## 11. 常见问题

### 请求返回 `404`

确认启动命令包含：

```text
--enable-file-streaming
```

同时确认正式环境没有误用 `/test/` 路径。

### 请求返回 `400 Invalid percent-encoding`

说明 `file_id` 的 URL 编码不合法。应使用语言标准库的路径段编码函数，不要手工替换字符。

### 下载立即成功但文件无法打开

检查调用方是否把二进制响应当成文本或 JSON 处理。必须按二进制流写入文件。

### 下载中途断开

删除临时文件并重新请求。必须比较实际字节数和 `Content-Length`，不能把提前断开的文件当成完整文件。

### 能否使用标准 `file_path`

不能。该端点需要 Telegram Bot API 对象中的 `file_id`。标准下载路径 `/file/bot<TOKEN>/<file_path>` 与本项目新增的 `/stream/file/bot<TOKEN>/<file_id>` 流式路由语义不同。

### 是否支持浏览器直接访问

不应让浏览器直连该端点或持有 Bot Token。应由业务后端或受控的签名下载层转发给客户端，并将 Bot API 服务的来源白名单限制为该代理。
